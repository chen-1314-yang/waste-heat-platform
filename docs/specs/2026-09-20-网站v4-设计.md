# 工业余热回收项目 · 网站 v4（实验版）设计文档

日期：2026-09-20
状态：待用户评审

---

## 1. 定位与目标

**v4 是一个实验性网站，与线上 v3 并存，不替换它。**

它存在的意义是：项目在路演之后仍在往前走（造价校准、外部证据补充、算法创新线），
需要一个**能持续改动**的载体。线上 v3 已经和提交出去的申报书、视频、材料对齐，
是冻结的；v4 是活的。

**"成熟后并入老站"的具体含义**：把 v4 构建出的 `dist/` 产物发布到老站所在的线上地址，
使线上内容切换到 v4；老站的原始文件**归档保留、不删除**（保留回退能力）。
因此 v4 的产物必须能独立部署，且不依赖 v4 目录下的任何构建期东西。

### 目标

1. 承载项目**持续演进**的内容，且改动成本低（改内容不动代码）。
2. 保住 v3 的全部硬能力：决策演示、实时模拟、帕累托、LCA、工况库、数据接入协议。
3. 新增 v3 没有的三层：**外部证据层、校准工作台、演进日志**。
4. 明确标注"实验版"，不与已提交材料混淆。
5. 保持**零外部依赖、离线可用**（v3 已验证：0 个外链）。

### 非目标（明确不做）

- 不做用户账号、登录、后端数据库。
- 不重写决策内核。v4 复用既有内核，只做接线。
- 不做多语言、SEO、埋点统计。
- **不改动线上 v3 的任何文件**。
- 暂不追求"部署上线"（受权限阻塞，见第 8 节）。

## 2. 关键约束

| 约束 | 来源 | 影响 |
|---|---|---|
| 零外部依赖、离线可用 | v3 现状（0 外链） | 不引 CDN，图表自绘或内联 |
| 内容与代码分离 | 用户要求"随进度不停改" | 内容全部数据驱动 |
| 不与已提交材料冲突 | 申报书/视频已提交 | 数字若变更必须显式标注版本与日期 |
| 成熟后并入老站 | 用户本轮明确 | 产物需可直接部署到静态托管 |
| 视觉与路演 PPT 统一 | PPT 已定"水乡墨绿" | v4 沿用该基底，不再另立一套 |

## 3. 架构：一份源，两种产物

```
site-v4/
├── content/                  内容与数据（日常只改这里）
│   ├── site.json             站点元信息：标题、团队、版本、横幅文案
│   ├── project.json          项目主张、背景、方法、创新点
│   ├── evidence.json         外部证据层
│   ├── calibration.json      校准工作台
│   ├── boundaries.json       诚实性边界
│   ├── changelog.json        演进日志
│   └── demo/                 决策演示所需数据（自 v3 迁移）
├── src/
│   ├── styles/               样式（CSS 变量 + 组件样式）
│   ├── engine/               决策内核（自 v3 移植，纯函数）
│   ├── views/                各页签的渲染逻辑
│   └── app.js                装配与路由
├── build.py                  构建脚本
└── dist/
    ├── site/                 多文件站点（部署用）
    └── 工业余热回收_实验版v4_单文件.html
```

**构建脚本做两件事**：把 `content/` 内联进模板生成单文件版；同时输出多文件版供部署。
两个产物内容必然一致——这修掉了 v3 里"线上版与单文件版可能不一致"的隐患。

## 4. 内容模型

### 4.1 evidence.json —— 外部证据层（新增）

```json
{
  "items": [
    {
      "id": "orc-world-map-953",
      "title": "全球 ORC 装机数据库",
      "value": "953 台 / 3512.7 MW",
      "scope": "工业余热回收 331 台；中国境内 31 台；水泥 12 台；冶金 33 台",
      "kind": "external-dataset",
      "grade": "公开可下载",
      "source": "ORC World Map（Tartière），厂商官网+新闻+论文交叉核对",
      "url": "https://github.com/tartieret/ORC-World-Map-SPA",
      "caveat": "无热源温度、无效率；953 台中 741 台工质缺失；含年份脏值"
    }
  ]
}
```

每条**必须带 caveat**（适用边界），没有 caveat 的条目不允许入库。

计划收录：953 台装机库、EU28 工业过程与余热（TNO）、10 项中国国家标准、
膨胀机效率图谱、R245fa/R1233zd 冷凝传热数据、HeatScout 9 个实测案例、
EPFL-IEA ORC 热经济模型、PyPSA 造价库、CIETO 温度区间。

### 4.2 calibration.json —— 校准工作台（新增，标注"进行中"）

```json
{
  "status": "in-progress",
  "items": [
    {
      "id": "orc-unit-cost",
      "parameter": "ORC 单位造价",
      "kernel_value": "23800 元/kW（固定单价）",
      "external": [
        {"source": "中国工程口径", "value": "6400-8700 元/kW", "scope": "蒸汽路径 6-9 MW"},
        {"source": "HeatScout 关联式", "value": "C = 3000 x Q^0.75 EUR（含安装 x1.6）"},
        {"source": "PyPSA 技术造价库", "value": "1376 EUR/kW_el",
         "source_ref": "Tartiere and Astolfi 2017"}
      ],
      "finding": "内核用 91.5 kW 小机组固定单价代表全规模（100 kW-20 MW），属量纲不匹配",
      "impact": "若切换口径，ORC 隐含回收期由 5.6 年降至 1.2-2.9 年，可能翻转推荐结论",
      "decision": "pending"
    }
  ]
}
```

decision 取值：pending / accepted / rejected。**未拍板的项必须显示为待定**。

### 4.3 boundaries.json —— 诚实性边界（新增）

沿用 v3 已有的诚实口径，结构化：

| 项目 | 口径 | 等级 |
|---|---|---|
| ORC 减碳量 | 仿真净功率 x 运行小时 x 电网因子 | 推算，非实测 |
| 供热减碳 | 替代天然气估算 | 演示估算 |
| 成本/回收期 | 代理模型 | 示意，非报价 |
| 工况库非公开案例 | 工程示例 | 示意 |
| TOPSIS 指标 | 典型演示值 | 待替换 |

### 4.4 changelog.json —— 演进日志（新增，本设计的核心）

```json
{
  "entries": [
    {
      "date": "2026-09-20",
      "version": "v4.0",
      "title": "实验版起步",
      "changes": ["自 v3 迁移决策演示", "新增外部证据层", "新增校准工作台"],
      "relative_to_v3": "v3 数字与已提交材料一致；v4 中标注为待定的项尚未生效"
    }
  ]
}
```

**演进日志是"更新版"身份的主要载体**——不靠一个标签，靠让页面自己展示改了什么。
每个版本条目必须写清"相对 v3 改了什么、有没有影响已提交材料的口径"。

导航顺序即叙事顺序：

| 页签 | 内容 | 相对 v3 |
|---|---|---|
| 概览 | 一页看懂：主张、背景、方法、关键数字卡 | 新增 |

点击可跳转到演进页。

## 6. 视觉方向

- **基底**：沿用路演 PPT 已定的"水乡墨绿"——墨绿主色 + 大量留白 + 克制的绿植感，
  保证网站与 PPT、申报书视觉统一。
- **数据色**：在墨绿基底上限定一组数据色（不超过 4 色），避免 v3 曾出现的"颜色太花"。
- **字体**：中文用思源宋体 / 微软雅黑体系，数字与英文用衬线数字以体现科研感；
  不引入外部字体文件（保持离线）。
- **图表**：自绘 SVG / canvas，无图表库依赖；坐标轴范围按数据实况设定，
  避免出现"几条线挤在一起看不出差别"的图（这是 PPT 阶段反复被指出的问题）。

## 7. 技术选型与理由

| 选择 | 理由 |
|---|---|
| 纯静态 HTML/CSS/JS，不用框架 | 保证单文件可提交、离线可用、无构建依赖 |
| 构建脚本用 Python | 本机已有 Python，且与项目其他脚本一致 |
| 图表自绘 | 避免 CDN 依赖；也避免图表库默认样式与设计冲突 |
| 决策内核沿用 v3 的纯函数实现 | 内核已验证（Python 与 JS 对拍 11 场景 0 差异），重写无收益 |

## 8. 部署（当前阻塞）

**阻塞原因**：新站要"可更新地上线"，需要一个能写入的 GitHub 令牌；
现有 codex-search 令牌是**公开仓库只读**，不能建仓库、不能上传。

**三条可选路径**（尚未决定，不在本设计范围内）：

1. 新建一个写入范围的令牌，用 GitHub API 上传（不经 git，规避本机 schannel 问题）。
2. 用不依赖 GitHub 的静态托管（Netlify / Cloudflare Pages 拖拽部署）。
3. 先不部署，只产出单文件版 + 本地预览，成熟后再一次性上线。

**本设计不依赖部署**：dist 产物先满足"本地打开 + 单文件提交"两个用途。

---

## 9. 风险

| 风险 | 应对 |
|---|---|
| 变成第二个没人维护的站点 | 内容与代码分离，改内容不动代码 |
| 校准数字与已提交材料冲突 | 校准项默认 pending，不进入演示数值；变更需用户拍板 |
| 视觉重蹈 PPT 阶段的反复 | 沿用已定"水乡墨绿"，不重新选色 |
| 单文件体积过大 | 构建时压缩；数据按页签分块内联 |
| 与老站内容漂移 | 演进日志强制记录差异 |

## 10. 验收标准

1. 断网打开单文件版，六个**顶层**页签（概览 / 决策演示 / 外部证据 / 校准 / 边界 / 演进）
   全部可用；决策演示内部的六个子页签同样可用。
2. 改 content 中任一 JSON，重新构建后页面内容随之变化，**无需改代码**。
3. 概览、外部证据、校准、边界、演进五页内容完整且标注口径。
4. 决策演示的数值仍与 v3 一致（未经拍板的校准项不生效）。
5. 页面明确标注"实验版"，且可跳转到与 v3 的关系说明。
